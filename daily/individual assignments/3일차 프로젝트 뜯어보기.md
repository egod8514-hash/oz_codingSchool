# 3일차 프로젝트 뜯어보기

> FastAPI 프로젝트 템플릿의 디렉터리와 파일이 어떤 책임을 가지는지 이해하고, SQLAlchemy·Alembic을 사용해 데이터베이스와 API를 연결하는 전체 흐름을 정리한 학습 문서입니다.
>
> 이 문서의 코드는 설명을 위한 예시입니다. 실제 프로젝트에서는 템플릿에 이미 정의된 클래스명, 설정명, import 경로, 동기/비동기 방식에 맞춰 수정해야 합니다.

## 1. 먼저 이해할 것: 한 요청이 처리되는 경로

사용자가 `POST /api/v1/users` 요청을 보냈다고 가정해보겠습니다.

```text
클라이언트
  ↓ HTTP 요청
app/apis/users.py
  ↓ 요청 형식 검증, 의존성 주입
app/services/user_service.py
  ↓ 회원가입 규칙과 비즈니스 로직 처리
app/repositories/user_repository.py
  ↓ SQLAlchemy를 이용한 데이터베이스 조회/저장
app/core/db/databases.py
  ↓ Engine과 Session을 통해 DB 연결
데이터베이스
  ↑ 저장 결과
app/schemas/user.py
  ↑ 응답 형식으로 변환
클라이언트
```

각 계층은 서로 다른 질문에 답합니다.

- **API**: 어떤 URL과 HTTP 메서드를 제공할 것인가?
- **Schema**: 입력과 출력 데이터의 모양이 올바른가?
- **Service**: 이 기능의 업무 규칙은 무엇인가?
- **Repository**: 데이터를 어떻게 조회하고 저장할 것인가?
- **Model**: 데이터베이스 테이블을 Python 객체로 어떻게 표현할 것인가?
- **Core/DB**: 설정과 데이터베이스 연결을 어떻게 공통 관리할 것인가?

이렇게 역할을 나누면 회원가입 규칙을 바꾸더라도 라우터나 SQLAlchemy 연결 코드를 모두 수정하지 않아도 됩니다. 반대로 API 함수 안에 검증, 비즈니스 규칙, SQL문을 전부 넣으면 기능이 커질수록 테스트와 유지보수가 어려워집니다.

FastAPI 공식 문서도 규모가 커지는 애플리케이션에서는 `APIRouter`로 경로 연산을 모듈화한 뒤 `app.include_router()`로 메인 앱에 등록하는 방식을 설명합니다. [1]

## 2. 디렉터리별 역할

### 2.1 `app/core/`

`core`는 애플리케이션 여러 곳에서 공통으로 사용하는 기반 기능을 모아두는 디렉터리입니다.

일반적으로 다음과 같은 파일이 들어갑니다.

```text
app/core/
├── config.py      # 환경 변수와 프로젝트 설정
├── security.py    # 비밀번호 해시, JWT, 인증 관련 공통 기능
└── db/
    └── databases.py  # Engine, Session, Base, DB dependency
```

`core`에는 특정 API의 업무 규칙을 넣지 않는 것이 좋습니다. 예를 들어 `회원가입 시 이메일 중복을 검사한다`는 규칙은 `services`에 있어야 하고, `DATABASE_URL을 어디서 읽을지`는 `core/config.py`에 있어야 합니다.

#### 학습용 사례

개발·테스트·운영 환경마다 데이터베이스 주소가 다르다고 가정합니다.

```env
# .env.example
APP_NAME=Study API
DATABASE_URL=sqlite:///./local.db
DEBUG=true
```

`.env`는 비밀값을 포함할 수 있으므로 Git에 올리지 않고, `.env.example`만 공유하는 것이 안전합니다.

### 2.2 `app/models/`

`models`는 데이터베이스의 테이블을 SQLAlchemy ORM 클래스로 표현하는 곳입니다. 클래스 하나가 테이블 하나를 나타내고, 클래스의 컬럼 속성이 테이블의 컬럼에 대응합니다.

SQLAlchemy 2.0 스타일의 간단한 예시는 다음과 같습니다.

```python
# app/models/user.py
from datetime import datetime

from sqlalchemy import DateTime, String, func
from sqlalchemy.orm import Mapped, mapped_column

from app.core.db.databases import Base


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    name: Mapped[str] = mapped_column(String(50))
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )
```

이 클래스는 `users` 테이블과 `id`, `email`, `name`, `created_at` 컬럼을 표현합니다. SQLAlchemy 공식 문서의 선언적 매핑도 `DeclarativeBase`, `Mapped`, `mapped_column()`을 사용해 Python 타입과 데이터베이스 메타데이터를 함께 정의합니다. [2]

`models`에 작성할 내용은 다음과 같습니다.

1. 테이블 이름인 `__tablename__`
2. 기본키, 외래키, 인덱스, 유니크 제약조건
3. 컬럼 타입과 nullable 여부
4. 테이블 사이의 관계가 있다면 `relationship`

모델은 데이터베이스 구조를 표현합니다. 요청 검증용 비밀번호 평문이나 API 응답에 노출하면 안 되는 내부 필드를 모델 하나로 해결하려 하지 말고, `schemas`를 별도로 둬야 합니다.

### 2.3 `app/repositories/`

`repositories`는 데이터베이스에 접근하는 코드를 모아둡니다. 즉, SQLAlchemy `Session`을 사용해 모델을 조회·생성·수정·삭제하는 계층입니다.

```python
# app/repositories/user_repository.py
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.user import User


class UserRepository:
    def get_by_email(self, db: Session, email: str) -> User | None:
        statement = select(User).where(User.email == email)
        return db.scalar(statement)

    def create(self, db: Session, user: User) -> User:
        db.add(user)
        db.flush()
        db.refresh(user)
        return user
```

Repository의 책임은 `이메일로 User를 찾는다`, `User를 저장한다`처럼 데이터 접근 방법에 집중하는 것입니다. `이미 가입한 이메일이면 어떤 HTTP 상태 코드를 반환할지` 같은 정책은 API 또는 Service가 결정해야 합니다.

`db.commit()`의 위치는 템플릿의 트랜잭션 설계에 맞춰야 합니다. 작은 예제에서는 repository가 commit할 수 있지만, 여러 repository 작업을 하나의 업무 단위로 묶어야 하는 서비스에서는 service가 commit과 rollback을 관리하는 편이 더 안전합니다.

### 2.4 `app/schemas/`

`schemas`는 Pydantic 모델을 이용해 API의 입력과 출력을 정의합니다. SQLAlchemy 모델이 **DB 테이블의 모양**을 표현한다면, Pydantic schema는 **API로 주고받는 데이터의 계약**을 표현합니다.

```python
# app/schemas/user.py
from datetime import datetime

from pydantic import BaseModel, ConfigDict, EmailStr


class UserCreate(BaseModel):
    email: EmailStr
    name: str
    password: str


class UserRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    email: EmailStr
    name: str
    created_at: datetime
```

`UserCreate`에는 회원가입 요청에 필요한 평문 비밀번호가 있지만, `UserRead`에는 비밀번호가 없습니다. 이 구분이 없으면 DB의 내부 필드가 실수로 API 응답에 포함될 수 있습니다.

Pydantic schema가 담당하는 예시는 다음과 같습니다.

- 이메일 형식 검사
- 필수 필드 여부 검사
- 문자열 길이와 숫자 범위 검사
- 응답에 포함할 필드 선택
- ORM 객체를 API 응답 데이터로 변환

### 2.5 `app/services/`

`services`는 애플리케이션의 비즈니스 규칙을 담당합니다. 여러 repository 호출을 조합하거나, 저장 전에 중복 여부를 확인하거나, 비밀번호를 해시하는 작업이 이 계층에 적합합니다.

```python
# app/services/user_service.py
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import Session

from app.models.user import User
from app.repositories.user_repository import UserRepository
from app.schemas.user import UserCreate


class UserAlreadyExistsError(Exception):
    pass


class UserService:
    def __init__(self, repository: UserRepository) -> None:
        self.repository = repository

    def create_user(self, db: Session, user_in: UserCreate) -> User:
        if self.repository.get_by_email(db, user_in.email):
            raise UserAlreadyExistsError

        user = User(
            email=user_in.email,
            name=user_in.name,
            # 실제 서비스에서는 평문 비밀번호를 저장하지 않고 해시합니다.
            password_hash=hash_password(user_in.password),
        )
        try:
            return self.repository.create(db, user)
        except IntegrityError:
            db.rollback()
            raise UserAlreadyExistsError


def hash_password(password: str) -> str:
    # 예시 자리입니다. 실제 프로젝트의 security 모듈 또는 검증된 해시 라이브러리를 사용합니다.
    return f"hashed:{password}"
```

위 코드는 학습용 단순화 예시입니다. 실제 프로젝트에서는 비밀번호를 직접 문자열로 저장하지 말고 `app/core/security.py`에 해시 함수를 분리합니다. 또한 경쟁 상태 때문에 사전 중복 검사만으로는 충분하지 않으므로 DB의 `unique=True` 제약조건도 함께 둬야 합니다.

### 2.6 `app/apis/`

`apis`는 외부 클라이언트와 직접 통신하는 API 라우터를 모아두는 디렉터리입니다. 프로젝트에 따라 `routers`, `api`, `endpoints`라는 이름을 사용하기도 합니다. 템플릿이 `app/apis/`를 사용한다면 그 명칭을 따르되, 핵심 책임은 동일합니다.

API 파일에서는 다음 작업만 담당하도록 유지하는 것이 좋습니다.

1. URL과 HTTP 메서드 선언
2. 요청 schema와 응답 schema 지정
3. `Depends()`를 통한 DB 세션·인증 정보 주입
4. service 호출
5. service 결과를 HTTP 응답 또는 예외로 변환

```python
# app/apis/users.py
from fastapi import APIRouter, Depends, HTTPException, status
from sqlalchemy.orm import Session

from app.core.db.databases import get_db
from app.schemas.user import UserCreate, UserRead
from app.services.user_service import (
    UserAlreadyExistsError,
    UserService,
)

router = APIRouter(prefix="/users", tags=["users"])
user_service = UserService(...)


@router.post(
    "",
    response_model=UserRead,
    status_code=status.HTTP_201_CREATED,
)
def create_user(user_in: UserCreate, db: Session = Depends(get_db)) -> UserRead:
    try:
        user = user_service.create_user(db, user_in)
    except UserAlreadyExistsError:
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail="이미 가입된 이메일입니다.",
        )
    return user
```

라우터 함수 안에서 직접 `db.query(...)`를 반복하거나 복잡한 업무 규칙을 작성하면 API 계층과 DB 계층이 강하게 결합됩니다. 라우터는 HTTP와 애플리케이션 로직 사이의 어댑터라고 생각하면 됩니다.

## 3. 파일별 역할

### 3.1 `app/main.py`

`main.py`는 FastAPI 애플리케이션의 시작점입니다.

주요 책임은 다음과 같습니다.

- `FastAPI()` 인스턴스 생성
- 애플리케이션 이름, 버전, 설명 설정
- `app/apis/`의 router 등록
- 공통 middleware 또는 lifespan 등록
- 상태 확인용 health check 제공

```python
# app/main.py
from fastapi import FastAPI

from app.apis import users

app = FastAPI(
    title="Study API",
    version="0.1.0",
)

app.include_router(users.router, prefix="/api/v1")


@app.get("/health", tags=["health"])
def health_check() -> dict[str, str]:
    return {"status": "ok"}
```

`app.include_router()`를 사용하면 라우터 모듈에 정의된 경로들이 메인 FastAPI 애플리케이션에 등록됩니다. 공통 prefix와 tag를 메인 또는 상위 router에서 관리하면 API 버전 관리와 Swagger 문서 구성이 쉬워집니다. [1]

실행 명령은 템플릿에 따라 다르지만 일반적으로 다음과 같습니다.

```bash
uv run uvicorn app.main:app --reload
```

실행 후 `/docs`에서 Swagger UI를 확인하고, `/openapi.json`에서 생성된 OpenAPI 문서를 확인합니다.

### 3.2 `app/core/config.py`

`config.py`는 환경 변수와 애플리케이션 설정을 한 곳에서 관리합니다. 코드 곳곳에서 `os.getenv()`를 직접 호출하지 않고 설정 객체를 주입하거나 import하면 설정 이름과 타입을 통일할 수 있습니다.

Pydantic Settings를 사용하는 예시입니다.

```python
# app/core/config.py
from functools import lru_cache

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    app_name: str = "Study API"
    database_url: str = "sqlite:///./local.db"
    debug: bool = False

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
    )


@lru_cache
def get_settings() -> Settings:
    return Settings()


settings = get_settings()
```

이 파일을 작성할 때 확인할 사항은 다음과 같습니다.

- 설정 이름이 `.env`의 환경 변수 이름과 일치하는가?
- 운영 환경의 비밀값을 소스 코드에 하드코딩하지 않았는가?
- 기본값이 개발 환경에서만 안전하게 동작하는가?
- `DATABASE_URL`을 동기 드라이버와 비동기 드라이버 중 어떤 방식으로 사용할 것인가?

### 3.3 `pyproject.toml`

`pyproject.toml`은 Python 프로젝트의 메타데이터와 의존성, 도구 설정을 관리하는 표준 설정 파일입니다. 이 템플릿에서는 특히 다음을 확인합니다.

- 프로젝트 이름과 버전
- 지원 Python 버전
- FastAPI, Uvicorn, SQLAlchemy, Alembic, Pydantic Settings 등 런타임 의존성
- pytest, ruff, mypy 같은 개발 의존성
- 빌드 시스템과 패키지 설정

개념적인 예시는 다음과 같습니다.

```toml
[project]
name = "study-api"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "alembic>=1.13",
    "fastapi>=0.115",
    "pydantic-settings>=2.0",
    "sqlalchemy>=2.0",
    "uvicorn[standard]>=0.30",
]

[dependency-groups]
dev = [
    "pytest>=8.0",
    "ruff>=0.6",
]
```

실제 버전과 의존성은 템플릿의 파일을 기준으로 해야 합니다. 이미 `uv.lock`이 있다면 임의로 버전을 크게 바꾸기보다 `uv add 패키지명`을 사용해 `pyproject.toml`과 lock 파일을 함께 갱신하는 것이 안전합니다.

### 3.4 `uv.lock`

`uv.lock`은 `pyproject.toml`의 의존성 범위를 실제 설치 가능한 구체적인 버전과 패키지 정보로 고정한 lockfile입니다. 팀원이 각자 설치해도 같은 의존성 해석 결과를 얻도록 도와줍니다.

`pyproject.toml`이 “어떤 버전 범위를 허용할지”를 적는 파일이라면, `uv.lock`은 “이번 프로젝트에서 실제로 어떤 버전을 선택했는지”를 기록하는 파일입니다.

자주 사용하는 명령은 다음과 같습니다.

```bash
# 의존성 추가
uv add fastapi sqlalchemy alembic

# 개발 의존성 추가
uv add --dev pytest ruff

# lockfile 생성 또는 갱신
uv lock

# lockfile 기준으로 환경 동기화
uv sync

# lockfile이 최신인지 검사하고 실행
uv lock --check
uv run --locked pytest
```

uv 공식 문서에 따르면 lock은 의존성을 해석하는 과정이고, sync는 lockfile에서 프로젝트 환경으로 패키지를 설치하는 과정입니다. `uv run`은 기본적으로 필요한 경우 lock과 sync를 자동 수행하며, CI에서는 `--locked`로 lockfile이 변경되지 않았는지 검사할 수 있습니다. [4]

`uv.lock`은 보통 소스 저장소에 커밋합니다. 반면 `.venv`, `.env`, 실행 중 생성되는 SQLite 파일 등은 `.gitignore`에 넣습니다.

## 4. 데이터베이스 연결 설정

### 4.1 `app/core/db/databases.py`의 책임

`databases.py`는 데이터베이스 연결을 애플리케이션 전체에서 재사용할 수 있게 준비하는 파일입니다. 일반적으로 다음 요소를 정의합니다.

1. **Engine**: 데이터베이스 연결을 만들고 connection pool을 관리합니다.
2. **Session factory**: 요청이나 작업 단위마다 사용할 Session을 만듭니다.
3. **Base**: SQLAlchemy 모델이 상속할 선언적 기반 클래스입니다.
4. **get_db**: FastAPI dependency로 Session을 열고 닫습니다.

SQLAlchemy의 `Engine`은 데이터베이스 연결을 생성하고 connection pool을 보유합니다. `Session`은 ORM 객체의 조회와 변경을 트랜잭션 단위로 관리합니다. [2]

### 4.2 동기 SQLAlchemy 연결 예시

```python
# app/core/db/databases.py
from collections.abc import Generator

from sqlalchemy import create_engine
from sqlalchemy.orm import DeclarativeBase, Session, sessionmaker

from app.core.config import settings


class Base(DeclarativeBase):
    pass


connect_args = {}
if settings.database_url.startswith("sqlite"):
    connect_args = {"check_same_thread": False}

engine = create_engine(
    settings.database_url,
    connect_args=connect_args,
    pool_pre_ping=True,
)

SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    autocommit=False,
)


def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

`get_db`는 요청마다 Session을 제공하고 요청 처리가 끝나면 닫습니다. `yield` 전후의 코드를 이용해 자원 정리를 보장하는 패턴입니다.

### 4.3 비동기 연결을 사용할 때

템플릿이 `AsyncSession`을 사용한다면 동기 예시를 그대로 섞으면 안 됩니다. 비동기 DB 드라이버와 `create_async_engine`, `async_sessionmaker`, `async def get_db()`를 한 세트로 사용해야 합니다.

```python
from collections.abc import AsyncGenerator

from sqlalchemy.ext.asyncio import (
    AsyncSession,
    async_sessionmaker,
    create_async_engine,
)

engine = create_async_engine(settings.database_url)
AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)


async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        yield session
```

동기와 비동기 중 어느 쪽이 더 좋은지보다 중요한 것은 프로젝트 전체에서 한 방식을 일관되게 사용하는 것입니다. 드라이버 URL도 동기용과 비동기용이 다를 수 있으므로 `pyproject.toml`, `.env`, DB 모듈을 함께 확인해야 합니다.

## 5. SQLAlchemy로 모델 작성하기

### 5.1 작성 순서

새로운 `Post` 기능을 추가한다고 가정하면 다음 순서로 진행합니다.

1. 테이블에 필요한 컬럼과 제약조건을 설계합니다.
2. `app/models/post.py`에 SQLAlchemy 모델을 작성합니다.
3. `app/models/__init__.py` 또는 모델 import 모듈에서 모델이 로드되도록 합니다.
4. Alembic이 모델을 인식하도록 `target_metadata`에 Base metadata를 연결합니다.
5. 마이그레이션을 생성하고 내용을 검토합니다.
6. DB에 마이그레이션을 적용합니다.
7. schema, repository, service, API를 연결합니다.

### 5.2 게시글 모델 사례

```python
# app/models/post.py
from datetime import datetime

from sqlalchemy import DateTime, ForeignKey, String, Text, func
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.core.db.databases import Base


class Post(Base):
    __tablename__ = "posts"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200), index=True)
    content: Mapped[str] = mapped_column(Text)
    author_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )

    author: Mapped["User"] = relationship()
```

관계 모델에서는 외래키가 가리키는 테이블이 실제로 존재하는지, 삭제 시 동작을 어떻게 할지, 순환 import가 생기지 않는지 확인해야 합니다. 규모가 있는 프로젝트에서는 관계 설정을 별도 모듈이나 문자열 annotation으로 조정하기도 합니다.

## 6. Alembic으로 마이그레이션 수행하기

### 6.1 마이그레이션이 필요한 이유

`Base.metadata.create_all()`은 현재 모델을 보고 테이블을 만들 수 있지만, 이미 운영 중인 데이터베이스의 스키마가 어떻게 변경되어 왔는지 기록하지 못합니다. 협업과 운영 환경에서는 `users` 테이블에 `nickname` 컬럼을 추가한 과정 자체가 코드로 남아야 합니다.

Alembic은 SQLAlchemy를 기반으로 관계형 데이터베이스의 스키마 변경을 관리하는 도구입니다. Alembic 환경은 보통 `alembic.ini`, `alembic/env.py`, `alembic/versions/`로 구성됩니다. [3]

### 6.2 초기화

프로젝트에 Alembic 환경이 없다면 한 번만 실행합니다.

```bash
uv add alembic
uv run alembic init alembic
```

이미 템플릿에 `alembic/`과 `alembic.ini`가 있다면 다시 init하지 않습니다.

### 6.3 `env.py` 설정의 핵심

Alembic이 SQLAlchemy 모델의 변경을 감지하려면 `env.py`가 애플리케이션의 `Base.metadata`를 알아야 합니다.

```python
# alembic/env.py의 핵심 개념 예시
from app.core.db.databases import Base
from app.models import post, user  # 모델 모듈을 import해 metadata에 등록


target_metadata = Base.metadata
```

모델을 import하지 않으면 클래스가 Python에 로드되지 않아 Alembic의 자동 비교 대상에 포함되지 않을 수 있습니다. 따라서 새 모델을 만든 뒤에는 모델 import 경로와 `target_metadata`를 반드시 확인합니다.

또한 `alembic.ini`에 DB URL을 고정해두기보다 프로젝트의 설정 객체를 사용하도록 템플릿 방식에 맞추는 것이 좋습니다. 비밀번호가 포함된 URL을 Git에 커밋하지 않도록 주의합니다.

### 6.4 마이그레이션 생성과 검토

모델에 변경을 만든 뒤 다음 명령으로 migration 파일을 생성합니다.

```bash
uv run alembic revision --autogenerate -m "create posts table"
```

`--autogenerate`는 모델 metadata와 현재 DB 스키마를 비교해 후보 변경사항을 만들어줄 뿐, 항상 완벽한 migration을 보장하지는 않습니다. 생성된 `alembic/versions/<revision>_create_posts_table.py`를 직접 열어 다음을 확인해야 합니다.

- `upgrade()`가 원하는 테이블·컬럼·인덱스·외래키를 만드는가?
- `downgrade()`가 안전하게 되돌리는가?
- 데이터 손실을 일으키는 변경이 없는가?
- nullable, default, unique 제약조건이 의도와 맞는가?
- 이름 변경을 삭제 후 생성으로 잘못 인식하지 않았는가?

예시는 다음과 같습니다.

```python
from alembic import op
import sqlalchemy as sa


def upgrade() -> None:
    op.create_table(
        "posts",
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("title", sa.String(length=200), nullable=False),
        sa.Column("content", sa.Text(), nullable=False),
        sa.Column("author_id", sa.Integer(), nullable=False),
        sa.Column("created_at", sa.DateTime(timezone=True), nullable=True),
        sa.ForeignKeyConstraint(["author_id"], ["users.id"]),
        sa.PrimaryKeyConstraint("id"),
    )
    op.create_index("ix_posts_title", "posts", ["title"])


def downgrade() -> None:
    op.drop_index("ix_posts_title", table_name="posts")
    op.drop_table("posts")
```

### 6.5 마이그레이션 적용과 되돌리기

```bash
# 현재 DB를 가장 최신 revision으로 이동
uv run alembic upgrade head

# 현재 적용된 revision 확인
uv run alembic current

# migration 이력 확인
uv run alembic history

# 한 단계 되돌리기
uv run alembic downgrade -1
```

Alembic은 revision 사이의 `down_revision` 연결을 읽어 적용 순서를 결정합니다. 따라서 migration 파일을 임의로 삭제하거나 이미 공유된 migration 내용을 수정하면 팀원의 DB 상태와 충돌할 수 있습니다. 이미 배포된 migration은 새 migration으로 수정하는 것이 안전합니다. [3]

## 7. API 구현 흐름: 게시글 생성 사례

게시글 생성 기능을 구현할 때는 다음과 같이 계층을 연결합니다.

### 7.1 Schema 작성

```python
# app/schemas/post.py
from datetime import datetime

from pydantic import BaseModel, ConfigDict, Field


class PostCreate(BaseModel):
    title: str = Field(min_length=1, max_length=200)
    content: str = Field(min_length=1)


class PostRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    title: str
    content: str
    author_id: int
    created_at: datetime
```

### 7.2 Repository 작성

```python
# app/repositories/post_repository.py
from sqlalchemy.orm import Session

from app.models.post import Post


class PostRepository:
    def create(self, db: Session, post: Post) -> Post:
        db.add(post)
        db.flush()
        db.refresh(post)
        return post
```

### 7.3 Service 작성

```python
# app/services/post_service.py
from sqlalchemy.orm import Session

from app.models.post import Post
from app.repositories.post_repository import PostRepository
from app.schemas.post import PostCreate


class PostService:
    def __init__(self, repository: PostRepository) -> None:
        self.repository = repository

    def create_post(
        self,
        db: Session,
        author_id: int,
        post_in: PostCreate,
    ) -> Post:
        post = Post(
            title=post_in.title,
            content=post_in.content,
            author_id=author_id,
        )
        created = self.repository.create(db, post)
        db.commit()
        db.refresh(created)
        return created
```

### 7.4 API 작성

```python
# app/apis/posts.py
from fastapi import APIRouter, Depends, status
from sqlalchemy.orm import Session

from app.core.db.databases import get_db
from app.schemas.post import PostCreate, PostRead
from app.services.post_service import PostService

router = APIRouter(prefix="/posts", tags=["posts"])
post_service = PostService(...)


@router.post("", response_model=PostRead, status_code=status.HTTP_201_CREATED)
def create_post(
    post_in: PostCreate,
    db: Session = Depends(get_db),
) -> PostRead:
    # 실제 인증 기능이 있다면 현재 로그인한 사용자의 ID를 사용합니다.
    current_user_id = 1
    return post_service.create_post(db, current_user_id, post_in)
```

### 7.5 `main.py`에 등록

```python
from app.apis import posts

app.include_router(posts.router, prefix="/api/v1")
```

최종 호출 예시는 다음과 같습니다.

```bash
curl -X POST http://localhost:8000/api/v1/posts \
  -H 'Content-Type: application/json' \
  -d '{"title":"첫 글","content":"FastAPI를 공부했습니다."}'
```

처리 순서를 한 문장으로 정리하면 다음과 같습니다.

> JSON 요청이 schema 검증을 통과하고, API가 service를 호출하면, service가 업무 규칙에 따라 model 객체를 만들고, repository가 Session을 통해 저장한 뒤, schema가 저장 결과를 응답 JSON으로 변환합니다.
