# [2일차] Git 브랜치(Branch) 관리 전략 비교 분석

프로젝트를 진행할 때 코드 버전 관리를 위해 주로 **Git**과 **GitHub**를 사용합니다. **Git branch 전략**은 여러 명의 개발자가 서로 영향을 주지 않고 동시에 작업을 할 수 있게 하며, branch가 특정 기능이나 이슈에 대응하여 작업을 추적하고 버전 단위로 관리하여 프로젝트 관리와 배포의 안정성을 높여줍니다.

본 문서에서는 팀원들과 함께 학습한 두 가지 대표적인 전략인 **Git Flow**와 **GitHub Flow**의 특징과 차이점을 정리합니다.

---

## 1. 개요 및 구조 차이

### 💡 깃 플로우 (Git Flow)
* **정의**: 제품 출시 버전, 개발 버전, 기능, 출시 준비, 버그 수정 등 다양한 branch를 활용하여 체계적으로 관리하는 전략입니다.
* **사용 브랜치**: `master`(또는 `main`), `develop`, `feature`, `release`, `hotfix` 총 5가지 핵심 브랜치를 사용합니다.
* **적합한 환경**: 배포 주기가 길고 엄격한 테스트 및 정기적인 버전 관리가 필요한 대규모 프로젝트에 적합합니다.

### 💡 깃허브 플로우 (GitHub Flow)
* **정의**: 하나의 기본 branch(`master` 또는 `main`)와 그에 기능을 추가하기 위한 branch(`feature`) 두 개만으로 운영하여 간편하고 빠른 수정 배포를 가능하게 하는 전략입니다.
* **사용 브랜치**: `main`과 `feature` 중심의 단순한 구조를 유지합니다.
* **적합한 환경**: 수시로 배포가 일어나고 빠른 피드백이 중요한 웹 서비스나 스타트업, 지속적 통합/배포(CI/CD) 환경에 적합합니다.

---

## 2. 개별 코디네이터(개발자)의 자료 수정 공간

브랜치 전략에 관계없이, 개별 개발자가 다른 사람의 간섭 없이 '직접 자유롭게' 수정할 수 있는 공간과 승인을 받아야 하는 공간은 다음과 같이 구분됩니다.

* **자유롭게 수정 가능한 영역**: 본인이 생성한 기능 브랜치(`feature/*`) 또는 개인 포크(Fork) 저장소.
* **승인이 필요한 영역**: 팀원이 공용으로 사용하는 메인 브랜치(`main`, `develop` 등). 이곳의 자료를 수정하려면 반드시 수정을 마친 후 검토(Review) 요청을 거쳐야 합니다.

---

## 3. 브랜치 전략별 수정 및 반영 방식 차이

개별 코디네이터가 올린 자료를 수정하거나 반영할 때, 두 전략은 시스템적으로 큰 차이를 보입니다.

###  깃허브 플로우 (GitHub Flow)에서의 수정
> **"개별 코디네이터가 수정하고 반영하는 과정이 매우 빠르고 즉각적임"**
* **수정 방식**: `main`에서 브랜치를 파서 자료를 수정한 뒤, 메인 브랜치로 **Pull Request(PR)**를 보냅니다.
* **최종 반영**: 팀원의 리뷰를 받고 승인되어 메인에 합쳐지는(Merge) 즉시, **실제 서비스에 실시간으로 배포**되는 구조입니다. 중간 단계를 거치지 않아 반영 속도가 매우 빠릅니다.

###  깃 플로우 (Git Flow)에서의 수정
> **"수정본이 최종 반영되기까지 여러 단계의 검증과 승인을 거침"**
* **수정 방식**: 개별 코디네이터가 코드를 수정하더라도 곧바로 최종 배포본이 되지 않으며, 우선 개발 브랜치(`develop`)에 통합됩니다.
* **최종 반영**: `develop` ➔ `release` (추가 버그 수정 및 QA) 단계를 거쳐 최종적으로 `master`에 합쳐지며, **정기 배포일에 맞추어 안전하게 반영**됩니다. (단, 운영 중인 서비스의 긴급 수정은 `hotfix` 브랜치를 통해 예외적으로 빠르게 반영합니다.)

---

## 4. 한눈에 보는 핵심 비교 표

| 구분 | 깃허브 플로우 (GitHub Flow) | 깃 플로우 (Git Flow) |
| :--- | :--- | :--- |
| **복잡도** | 낮음 (매우 직관적이고 단순함) | 높음 (규칙과 브랜치가 많음) |
| **수정 후 반영 속도** | **매우 빠름** (수정 즉시 실시간 반영) | **비교적 느림** (단계별 검증 및 정기 배포) |
| **중간 검증 단계** | 없음 (`main`으로 바로 합침) | 많음 (`develop`, `release` 등 단계별 이동) |
| **주요 장점** | 신속한 개발과 즉각적인 서비스 업데이트 | 철저한 버전 관리와 안전한 테스트 기간 확보 |
| **추천 상황** | **수시로 수정하고 빠르게 배포해야 할 때** | **수정을 모아서 안전하게 정기 배포해야 할 때** |

# [과제 가이드] 이번 회원 관리 API 프로젝트에 GitHub Flow 전략이 적합한 이유

이번 과제(5개의 회원 관리 API 구현 및 유효성 검사)의 특성과 규모를 고려했을 때, 프로젝트 협업 및 버전 관리를 위해 **깃허브 플로우(GitHub Flow)** 방식을 사용하는 것이 훨씬 더 적합합니다. 그 명확한 이유와 추천 워크플로우를 아래와 같이 정리합니다.

---

## 1) GitHub Flow 전략이 적합한 이유

### 프로젝트 규모가 작고 단일 배포 환경입니다
* **과제 특성**: 본 과제는 혼자 또는 소규모 팀이 하나의 FastAPI 애플리케이션 내에 5개의 API를 구현하여 `main` 브랜치에 최종 제출(Push)하는 구조입니다.
* **적용 이점**: 굳이 복잡하게 `develop`, `release`, `hotfix` 등 여러 개의 관리용 브랜치를 유지할 필요가 전혀 없습니다. `main`에서 기능 브랜치를 파서 구현한 뒤 곧바로 합치는 **GitHub Flow**가 공수와 혼선을 크게 줄여줍니다.

###  빠른 실험과 즉각적인 피드백이 중요합니다
* **과제 특성**: Pydantic을 활용한 이메일/비밀번호 정규표현식 검증, 예외 처리(`404 Not Found`, `400 Bad Request`) 등 세부적인 기능 코드를 빠르게 테스트하고 수시로 고쳐야 합니다.
* **적용 이점**: **GitHub Flow**는 구조가 단순하여 수정한 코드를 즉시 메인 브랜치에 반영하고, 로컬에서 `Swagger UI(/docs)`를 띄워 검증하기에 매우 직관적이고 편리합니다. 반면 Git Flow는 기능 하나를 고칠 때마다 여러 단계의 브랜치를 거쳐야 하므로 과제 진행 속도가 저뎌질 수 있습니다.

### 실무 및 교육적 관점에서의 트렌드

* 최근 스타트업이나 현대적인 웹/앱 API 개발, 그리고 일 단위로 빠르게 완성해야 하는 해커톤이나 과제 전형에서는 **GitHub Flow(또는 이를 변형한 트렁크 기반 개발)**가 글로벌 표준처럼 널리 사용된다고 합니다.

---

## 2) 과제 진행을 위한 추천 워크플로우 (GitHub Flow 예시)

  **`main` 브랜치 최신화**
   * 작업의 기준이 되는 최신 메인 브랜치 상태에서 시작합니다.
  **기능(Feature) 브랜치 생성**
   * 회원 CRUD API 구현을 위한 전용 독립 브랜치를 생성합니다.
   ```bash
   git checkout -b feature/user-crud (제가 맡은 부분은 회원 정보 삭제 부분으로 "feature/delete-user" 브랜치를 생성해 분담을 맡은 해당 부분 코드 작업)
   ```
  **코드 작성 및 로컬 테스트**
   * `app/apis/practice_apis.py` 파일에 요구사항(정규표현식, 유효성 검사 등)에 맞춘 API 코드를 작성하고 Swagger UI에서 검증합니다.

  **원격 저장소 커밋 및 푸시**

   * 구현 완료 후 변경 사항을 로컬에 저장하고 원격 깃허브 저장소에 업로드합니다.
   ```bash
   git add .
   git commit -m "feat: 유저 관리 API 구현 및 정규표현식 예외 처리 추가"
   git push origin feature/user-crud
   ```
  **풀 리퀘스트(PR) 개설 및 병합(Merge)**

   * 깃허브 웹사이트에서 Pull Request(PR)를 생성하여 팀원들과 코드를 리뷰한 뒤, 최종 제출을 위해 `main` 브랜치에 안전하게 합칩니다.
